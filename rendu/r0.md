## Le **numéro de binôme : B2-1**

## 1\. CU-01 : Estimer le backlog d'un projet

| Rubrique | Contenu |
| :---- | :---- |
| **Portée et niveau** | application CAPI · utilisateur |
| **Acteur principal** | scrum master, développeurs et développeuses |
| **Intervenants et intérêts** | chef de produit: il s’intéresse à l’efficacité du produit. program manager (pm): il s’intéresse au déroulement du projet. le client : il s’intéresse à la conformité du produit à leurs besoins et au respect des délais de livraison. |
| **Déclencheur** | Les développeurs décident de commencer un projet. |
| **Garanties** | Minimales : En cas de problème pendant l’estimation, le système garantit que les résultats enregistrés ne seront pas perdus. Si la partie est interrompue quand les résultats ne sont pas encore enregistrés, les autres informations comme la liste des user stories ne seront pas perdues. De succès :Toutes les user stories du backlog ont été estimées et validées. Les résultats des estimations sont disponibles dans un fichier json téléchargeable. |

### Scénario nominal (5 à 7 étapes)

1. Le scrum master crée une session. (Le scrum master saisit le nombre de joueurs, choisit la règle de validation et importe un backlog au format JSON.) (CU-03)  
2. Les participants saisissent leurs pseudos tour par tour.   
3. Le système affiche la liste des fonctionnalités du backlog à estimer, Le scrum master sélectionne les fonctionnalités à estimer pour ce tour.  
   ~~Lister toutes les fonctionnalités qu’on doit avoir dans le produit final~~   
4. Voter sur une fonctionnalité (CU-02).  
5. Répéter 4\. jusqu’à validation pour toutes les fonctionnalités traitées.  
6. Le système exporte backlog estimé  
   

### Extensions (3 obligatoires)

- **\<1\>a.** Le backlog chargé est invalide :  
  - \<1\>a1 Le système affiche un message d'erreur et demande un nouvel import de backlog.  
  - \<1\>a2 Le scrum master importe un nouveau backlog.  
  - \<1\>a~~2~~3 Le système répète a1 et a2 jusqu’à backlog chargé valide.  
- **\<4-5\>a.** Tous les joueurs jouent la carte café :  
  - **\<4-5\> a1** Le système sauvegarde les paramètres de configuration, les résultats estimés, le backlog et la progression actuelle dans le JSON temporaire.  
  - **\<4-5\>a2** Le système crée une option de lancer partie sauvegardée au menu principal  
      
- **\<4-5\>b.** L'utilisateur reprend une partie sauvegardée :  
  - **\<4-5\>b1** Le scrum master choisit option de lancer une partie sauvegardée,  
  - **\<4-5\>b2** Le scrum master choisit la partie ~~qu’on~~ qu’il ou elle veut charger.  
  - **\<4-5\>b3** Le système charge le fichier JSON temporaire et continue la progression.

## 2\. CU-02 : Voter sur une fonctionnalité

| Rubrique | Contenu |
| :---- | :---- |
| **Portée et niveau** | application CAPI · utilisateur |
| **Acteur principal** | développeurs et développeuses, le scrum master |
| **Intervenants et intérêts** | Le scrum master : il veut connaître l’avance de l’estimation. développeurs et développeuses: Ils veulent connaître l’envergure et les efforts nécessaires pour chaque tâche.   |
| **Déclencheur** | Le scrum master lance un tour de vote. |
| **Garanties** | Minimales : Les votes précédents validés sont enregistrés dans le fichier JSON.  · De succès : La user story a été estimée et validée, le résultat a été bien enregistré dans le fichier et le prochain vote est prêt à être lancé. |

### Scénario nominal (5 à 7 étapes)

1. Le système affiche la User Story.  
2. Chaque joueur choisit une carte.  
3. Le système cache le résultat après chaque choix.  
4. Le système révèle les votes.  
5. Le système vérifie la règle de validation.  
6. Le système répète les étapes 1-5 jusqu’à la rencontre de la règle de validation.  
7. Le système enregistre le résultat dans le fichier JSON.

### Extensions (3 obligatoires)

- **\<5\>a.** Premier tour non unanime :  
  - \<5\>a1 Le scrum master initialise un débat quant aux réponses des participants.		  
  - \<5\>a2 Le scrum master relance un vote qui suivra la règle de validation choisie pendant Créer une session.(CU-03) (parmi:  moyenne, médiane, majorité absolue, majorité relative.)  
  - \<5\> a3 répéter a1-a2 jusqu’à conformité à la règle de validation.  
- **\<6\>a.** La règle choisie ne permet pas de valider l’estimation à partir du deuxième tour :   
  - \<6\> a1 Le scrum master prend la décision de changer de règle de validation   
  - \<6\> a2 Le scrum master relance un débat entre les participants  
  - \<6\> a3 Le scrum master relance un vote (étape 2 du scénario nominal)   
  - \<6\> a4 répéter a1-a2  jusqu’à validation  
  -   
  - ~~\<6\> b1 Le scrum master relance un débat entre les participants~~  
  - ~~\<6\> b2 Le scrum master relance un vote (étape 2 du scénario nominal)~~   
  - ~~\<6\> b3 Les acteurs répètent b1-b2 jusqu’à validation.~~   
  - ...  
- **\<2-6\>a.** Au moins un joueur joue la carte \<?\>:

  \<2-6\> a1 Le scrum master lance une discussion explicative sur la fonctionnalité.

  \<2-6\>a2 Le scrum master relance le vote (étape 2 du scénario nominal).

- **\<2\>b.** Tous les joueurs jouent la carte café :  
  - **\<2\> b1** Le système sauvegarde les paramètres de configuration, les résultats estimés, le backlog et la progression actuelle dans le JSON temporaire.  
  - **\<2\>b2** Le système crée une option de lancer partie sauvegardée au menu principal.

## 3\. Les 10-12 user stories

| US | Texte (En tant que... je veux... afin de...) | Source | MoSCoW |
| :---- | :---- | :---- | :---- |
| US-01 | En tant que scrum master, je veux pouvoir créer une session afin d’estimer un backlog de tâches. | CU-01,scénario nominal, étape 1 |  Must |
| US-02 | En tant que scrum master, je veux pouvoir lancer une partie sauvegardée depuis le menu principal afin de continuer d’estimer un backlog de tâches non-terminé | CU-01, extension 4-5a | Should |
| US-03 | En tant que participant/developpeur/developpeuse je veux pouvoir choisir une carte au moment du vote, afin de donner une estimation sur la fonctionnalité | CU-02,scénario nominal, étape 2 | Must |
| US-04 | En tant que Scrum master, je veux pouvoir choisir la règle de validation au moment de créer une session, afin de réguler les modalités de vote. | CU-01,scénario nominal, étape 1 | Must |
| US-05 | En tant que participant je veux pouvoir choisir la carte café afin de suggérer une pause. | CU-02,scénario nominal, étape 2 | should |
| US-06 | En tant que participant je veux pouvoir choisir la carte “?” afin d’exprimer mon incertitude à propos d’une fonctionnalité | CU-02,scénario nominal, étape 2 | Must |
| US-07 | En tant que scrum master et participants je veux que le système sauvegarde une partie interrompue par la carte café afin de pouvoir la recharger ultérieurement. | CU-01, extension 4-5a | should |
| US-08 | En tant que joueur, je veux que le système masque mon choix afin de ne pas influencer les choix des autres joueurs. | CU-02,scénario nominal, étape 3 | must |
| US-09 | En tant que scrum master, je veux pouvoir changer la règle de validation à partir du deuxième tour de chaque vote afin de pouvoir débloquer une situation répétitive. | CU-02 extension 6a | could |
| US-10 | En tant que scrum master, je veux que le premier tour de chaque vote se fasse suivant la règle stricte (unanimité) afin d’ouvrir le débat lors de désaccord au lieu de suivre directement une règle de validation choisie (par exemple la majorité) dès le premier tour  | CU-01,scénario nominal, étape 1 | Must  |

Parmi ces 6 US, 3 portent les règles de validation : règle stricte, règle choisie, premier tour à l'unanimité.
